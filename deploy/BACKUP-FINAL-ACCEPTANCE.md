# Итоговая приёмка backup и DR Karimoff

17.11.2026. Решение: реализованное локальное резервирование и проверенное
восстановление принимаются в ограниченном объёме. Полное соответствие всему §28
и готовность к потере VPS этим аудитом не подтверждаются. Production в ходе
итогового аудита не изменялся; использованы сохранённые доказательства выполнения.

## Соответствие ТЗ v0.9

Источник: Karimoff_TZ_v0.9 (1).docx, раздел 28 «Технические требования» из локальной
копии Downloads/Telegram Desktop. В разделе указано «Резервное копирование»;
конкретные RPO/RTO, сроки хранения и off-site там не заданы.

| Требование §28 | Статус текущего аудита |
|---|---|
| Резервное копирование | Выполнено для SQLite и uploads; штатный запуск и DR подтверждены |
| HTTPS/SSL | HTTPS-запрос в DR получил 200; полный аудит TLS/renewal не выполнялся |
| Авторизация админки | Не входит в проверенный backup/DR scope |
| Серверная валидация данных | Не входит в проверенный scope |
| Безопасная обработка uploads | Исключение симлинков в backup проверено; безопасность загрузочного API этим не доказана |
| Оптимизация изображений/скорость | Не проверено этим аудитом |
| Основные актуальные браузеры | Не проверено: HTTP smoke не заменяет браузерную матрицу |
| Cookie-уведомление | Не проверено этим аудитом |
| Нет обязательных интеграций 1С/CRM/склад | Backup таких зависимостей не добавляет |
| SEO/аналитика позднее, без архитектурных препятствий | Backup их не добавляет; общий архитектурный аудит не выполнялся |

## Ограничения и найденные риски

1. В выбранной БД 0 ссылок /uploads/. Проверка прошла, но непустые связи не покрыты.
   Следующий тест: синтетическая БД с image/video/document, HTML/JSON ссылками,
   отсутствующим файлом и попыткой выхода из каталога. Не добавлять данные в production.
2. SQLite backup целостен сам по себе; последовательный rsync uploads не является
   снимком одного момента и не гарантирует согласованность с БД. Нужны согласованный
   протокол записи/пауза изменений либо иной согласованный механизм snapshots.
3. Нет off-site-копии: потеря VPS затрагивает обычные и защищённые локальные backups.
   Полный rebuild ОС/Node/nginx/TLS/DNS, secrets recovery и почта не проверены.
4. Ротация uploads выключена. Два снимка по 3 305 472 байта = 6 610 944 байта;
   прогноз +99 164 160 байт/30 дней, +1 206 497 280 байт/год при одном запуске в день
   и постоянном объёме. Требуются контроль места/возраста копии и оповещение о failure.
5. flock координирует только сотрудничающие backup-процессы, не запись приложения.
   Защита путей предполагает доверенный root/тот же UID и отсутствие враждебной смены mounts/ACL.
6. Шаблон deploy/systemd/karimoff-backup.service уже содержит uploads ExecStartPost,
   а drop-in добавляет ещё один. Их совместная установка даст два запуска.
   Production прошёл путь «исходный unit + drop-in»; универсальный deploy-пакет
   перед коммитом должен иметь один источник команды. Исправление здесь не применялось.
7. Исходная SQLite retention pipeline без pipefail может маскировать промежуточную
   ошибку; политика не изменялась. Нужен отдельный review, не часть этой приёмки.
8. deploy/deploy.sh содержит chmod существующих backup и подавление ошибок через
   || true; этот provision нельзя считать эквивалентом согласованного rollout.
   Не запускать как часть backup-пакета без отдельной проверки.
9. DR привязан к дате, хешам кода и manifest одного запуска; следующая более новая
   копия требует пересмотра входов. Readiness отчётов «не выполнялось» — история
   подготовки, актуальный результат указан в этой приёмке.

## Зашифрованная внешняя копия — рекомендуемый следующий этап

Предложение: restic с клиентским шифрованием в отдельном аккаунте/у другого
провайдера через TLS rest-server append-only. Передавать завершённые пары SQLite/
uploads и manifest с идентификатором запуска/хешами; не копировать live SQLite
обычным файловым копированием. Согласовать атомарность пары отдельно.

Ключ репозитория и credentials — secret store/root0600, не Git и не командная строка;
резерв ключа офлайн у владельца. Credentials удаления/prune не выдавать VPS:
maintenance только с отдельного доверенного узла и по одобренной политике.
Append-only ограничивает удаления через клиент, но не заменяет защиту storage-admin:
нужна отдельная immutable/offline копия и независимое хранение ключа.

Предложенные целевые RPO ≤24 ч и RTO полного сервера ≤2 ч требуют согласования
и измерения; это не требования §28 и не уже достигнутые показатели.
Еженедельный check, регулярный read-data check и ежемесячное восстановление на
чистую VM; мониторинг возраста успешной копии и свободного места. Off-site retention
согласовать отдельно; существующую retention не менять, prune пока не выполнять.
